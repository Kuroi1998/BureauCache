# Audit QA de BureauCache

**23 novembre 2026 · BureauCache 3.3 · Windows et .NET Framework**

La revue porte sur les 38 fichiers C# de `src/` (7 263 lignes après correction), le script de compilation, le script de publication et le workflow GitHub Actions. Les constats ci-dessous proviennent de la lecture du code et des essais locaux précisés dans le tableau. La couverture d’exécution dépend de la configuration Windows, des fichiers disponibles et des opérations réellement déclenchées.

[`Calc.Format`](src/Search/Calc.cs) | 9 cas de format et d'aller-retour ajoutés. Suite complète : 145 réussis, 0 ignoré. |
| QA-16 | Haute | Ancien R-01. L'activité d'un dossier n'était estimée que sur ses métadonnées et 300 entrées directes : une modification récente dans un sous-dossier, ou après ces 300 entrées, passait inaperçue. `Archiver.ActivityOf` parcourt maintenant tout le contenu, sous-dossiers compris, et s'arrête au premier élément récent. Si le parcours échoue ou dépasse 5 000 entrées, l'ancienneté n'est pas confirmée et le dossier n'est pas rangé. [`Archiver.ActivityOf`](src/Core/Archiver.cs) | 9 tests sur des arborescences temporaires datées, dont un sous-dossier modifié à quatre niveaux, une modification après 400 entrées, le dépassement du budget et la copie récente d'un fichier ancien. |
| QA-17 | Haute | Ancien R-03. Il est maintenant reporté et retenté chaque minute tant que le panneau est occupé (`Busy`) ou qu'une annulation est en attente. `Archiver.Run` revérifie aussi chaque élément juste avant de le déplacer (cas de « Ranger maintenant » après confirmation). [`App.RunArchive`](src/App/App.cs) · [`Archiver.Run`](src/Core/Archiver.cs) | Revue du code et compilation. **Non vérifié dans l'application** : déclenchement du rangement pendant un renommage ouvert (scénario manuel décrit dans TASKS.md, T-004). |
| QA-18 | Haute | Revue croisée de QA-16 et QA-17 par ChatGPT, reproduite puis triée. Six défauts sont corrigés : (1) le rangement automatique déplaçait des candidats évalués plus tôt dans le lot ; chaque élément est maintenant évalué juste avant son déplacement. (2) Il pouvait se déclencher sous une fenêtre modale (confirmation de « Ranger maintenant », écrasement à l'export des réglages) ; il se reporte maintenant tant qu'une fenêtre de l'application est désactivée par un dialogue. (3) Une jonction ou un lien symbolique dans un dossier faisait juger le contenu d'un autre emplacement ; l'ancienneté n'est plus confirmée dans ce cas. (4) Les dates étaient comparées en heure locale, qui se répète au changement d'heure d'octobre ; la comparaison se fait en UTC. (5) Le journal d'annulation n'était enregistré qu'en différé ; il l'est immédiatement après un rangement. (6) Un dossier d'archive OneDrive « à la demande », qui est un point d'analyse sans être un lien, bloquait tout rangement ; seuls une jonction ou un lien sont refusés. [`Archiver`](src/Core/Archiver.cs) · [`App.ModalOpen`](src/App/App.cs) · [`Native.IsLink`](src/Core/Native.cs) | Tests de ChatGPT (`ArchiverReviewTests`), avec de vraies jonctions et le changement d'heure du fuseau de Paris : ils échouaient avant la correction. Suite : 161 réussis. Les points (2), (5) et (6) sont relus et compilés, **non vérifiés dans l'application**. |
| QA-19 | Moyenne | Ancien R-07. L'ancienne version était effacée dès le démarrage de la nouvelle, avant l'initialisation du panneau : un plantage au démarrage laissait l'utilisateur sans retour possible. Désormais, tant que `.old` existe, la nouvelle version est à l'essai : un marqueur `.trial` est posé au démarrage, puis effacé avec `.old` après 10 s de fonctionnement. Un démarrage qui trouve un marqueur non confirmé remet l'ancienne version en place (la version fautive est gardée en `.bad`), affiche un message et la relance. [`Updater.BeginStart`, `RollBack` et `ConfirmStart`](src/Core/Updater.cs) · [`Program.Main`](src/App/Program.cs) | 7 tests sur de faux exécutables (essai, confirmation, retour, retour impossible, nouvelle mise à jour). Renommage d'un exe en cours d'exécution vérifié sur Windows 11. **Non vérifié** : une vraie mise à jour suivie d'un plantage. **Limites** : un plantage après 10 s, ou une version qui démarre mais fonctionne mal, ne déclenche pas de retour. |
| QA-21 | Critique | Revue croisée de T-005 et T-006 par ChatGPT, reproduite puis triée. (1) **Brouillon piégé** : le script signait l'exe compilé par la CI, qu'un GitHub compromis peut remplacer. L'exe de la CI ne peut pas être comparé à une compilation locale (environ 81 000 octets d'écart mesurés sur la 3.3, faute de compilateur déterministe). `signer-version.ps1` recompile donc le tag sur le PC, sans exécuter de script du dépôt, vérifie que le tag de GitHub est le tag local, affiche les fichiers sensibles modifiés depuis la version précédente, puis relit ce que GitHub sert réellement avant de publier. (2) `ConfirmStart` pouvait effacer `.old` depuis l'ancien processus juste après un remplacement : il n'agit plus que si ce processus a commencé un essai et que le marqueur existe. (3) Une seconde mise à jour pendant un essai écrasait `.old` avec la version à l'essai : la version sûre est maintenant conservée. (4) Un marqueur `.trial` impossible à créer faisait annoncer un essai sans filet : `.old` est désormais gardé sans essai. (5) Un retour arrière interrompu entre ses deux déplacements ne pouvait pas reprendre. (6) Un BOM dans le `.sig` bloquait la mise à jour : il est ignoré. [`Updater`](src/Core/Updater.cs) · [`outils/signer-version.ps1`](outils/signer-version.ps1) | 5 tests de ChatGPT (`UpdaterSecurityReviewTests`), dont 4 échouaient avant la correction. Suite : 192 réussis. Compilation de référence et contrôle du tag essayés à blanc sur la 3.3. Cycle complet de publication réalisé avec la 3.4 (voir QA-20). |
| QA-20 | Haute | Ancien R-04. La mise à jour ne vérifiait qu'un SHA-256 publié par le même dépôt que l'exe. Les versions du dépôt officiel sont désormais signées (RSA-3072) avec une clé qui ne passe jamais par GitHub, et `Updater` refuse une version sans signature valide (D-004). [`Updater.VerifySignature`](src/Core/Updater.cs) · [`outils/signer-version.ps1`](outils/signer-version.ps1) | **3.4 publiée le 2026-11-23 par le circuit complet** : CI en brouillon, compilation locale, signature, publication. Contrôle après publication : `/releases/latest` renvoie la 3.4 avec l'exe, le `.sha256` et le `.sig` (les trois motifs de l'updater trouvés) ; version 3.4 ; empreinte conforme ; signature acceptée par `Updater.VerifySignature` avec les vraies clés et refusée pour un exe modifié ; clés embarquées dans l'exe publié identiques à celles du dépôt. **Reste à observer** : la mise à jour réelle depuis une installation 3.3, et le refus d'une version non signée par une installation 3.4 (dépôt de test). Risque résiduel de la transition : R-24. |
